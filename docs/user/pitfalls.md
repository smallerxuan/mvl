# MVL 陷阱合集

*真机踩坑记录：现象 → 根因 → 正确做法*

> **配套文档**：[design.md](../design/design.md)（架构设计）· [porting.md](porting.md)（移植指南）
> **严重级别定义**：
> 【致命】可致崩溃（HardFault / LoadProhibited）、堆损坏、死锁、整机复位
> 【高】功能错误但不崩：事件丢失、数据错乱、显示错误内容
> 【中】体验或集成问题：延迟、慢一帧、丢非关键更新

## 一、致命级

### P1 LVGL 任务内调用阻塞式 `mvl_msg_post()` —— 自我死锁 【致命】

- **现象**：某次 UI 操作后界面彻底假死，或触发看门狗复位；队列越满越容易复现。
- **根因**：`mvl_msg_post()` 在队列满时**永久阻塞**直到投递成功，而队列的唯一消费者就是 LVGL 主任务自己。在 LVGL 主任务（含 `mvl_msg` 回调、控件事件回调、`lv_timer` 回调）里调用它，等于让自己排队等自己——死锁。
- **正确做法**：已在 LVGL 主任务上下文时**直接调用 `lv_*()`**，不要再投递。识别准则：凡是经 `mvl_msg_process()` / `lv_timer` / LVGL 事件回调进入的代码，都在 LVGL 上下文。

### P2 ViewModel 回调发布会路由回 LVGL 的事件 —— 总线版自我死锁 【致命】

- **现象**：P1 的事件总线变体。ViewModel 回调里 `mvl_evt_publish()` 了一个**同样被 `MVL_EVT_CTX_LVGL` 订阅**的事件后，UI 假死。
- **根因**：LVGL 订阅者的投递路径是 `mvl_msg_post()`（阻塞版）。ViewModel 回调本身就运行在 LVGL 主任务（经 `dispatch_in_lvgl` 进入），此时走阻塞投递即回到 P1 的自我死锁。队列未满时不死锁，但事件被无意义地推到了下一周期。
- **正确做法**：LVGL 上下文里要联动 UI，**直接调 View 接口 / `lv_*()`**；确需跨模块级联，先合并 / 降频，避免在回调内发布。
- **排查**：逐事件检查「发布者上下文 × 订阅者上下文」矩阵，不允许存在 LVGL → LVGL 组合。

### P3 ctx 指向已销毁的局部变量 —— 回调中 HardFault 【致命】

- **现象**：`mvl_msg_post()` 投递后，回调执行时 HardFault / 数据是垃圾值；时好时坏，与任务调度时序相关。
- **根因**：投递是**异步**的——`post` 返回时回调还没运行。`ctx` 若指向投递函数的局部变量，回调执行时栈帧早已销毁。
- **正确做法**：按生命周期速查表选择 ctx 来源（[design.md](../design/design.md) §3.5）：≤ 指针宽度的数据用 `(void *)(uintptr_t)v` 数值强转（零风险）；多参数用 `static` / 全局结构体（注意多生产者互相覆盖）或 `malloc`（所有权随消息转移，**回调内 `free`**）。事件总线用户无此问题——载荷是 8 字节值拷贝。
- **排查**：全局 review 所有 `post` 调用点，凡出现 `&局部变量` 一律打回。

### P4 SMP 平台临界区不持锁 —— 双核真并发撕开投递池 【致命】

- **现象 A**：vanilla FreeRTOS 的临界区代码照搬到 ESP-IDF 直接**编译失败**（`too few arguments to vPortEnterCritical`）。
- **现象 B**：更隐蔽的情况——用了只关本核中断 / 挂本核调度的「临界区」，编译通过，但运行中偶发崩溃、堆损坏、丢事件，几小时到几天一次。
- **根因**：ESP-IDF 的 FreeRTOS 是 SMP 版本，两个核各自独立运行。`mvl_evt` 的 LVGL 投递池分配扫描 `s_pool_used[]` 数组，任务核与 ISR 核若不持同一把自旋锁，扫描会被真并发撕开。编译失败的现象 A 其实是救了你一命——它在提示临界区语义不成立。
- **正确做法**：SMP 平台临界区必须持 `portMUX_TYPE` 自旋锁（`taskENTER_CRITICAL(&mux)` / ISR 侧 `taskENTER_CRITICAL_ISR(&mux)`）。直接用仓库的 `port/esp_idf`；移植到其他 SMP 平台时同理，见 [porting.md](porting.md) §3.3。

### P5 LVGL 任务内同步调用阻塞型后台 API —— 看门狗复位 【致命】

- **现象**：点 UI 按钮数秒后整机复位（真机案例：控件事件回调内同步调用 `esp_wifi_disconnect()` / `esp_wifi_connect()`，8 秒后 TWDT 任务看门狗复位）。
- **根因**：控件事件回调运行在 LVGL 主任务。在其中同步调用阻塞型后台 API（WiFi 连接、网络请求、长延时 `vTaskDelay`），会拖垮整个任务调度，触发看门狗；即便不触发，UI 也会整体卡死相应时长。
- **正确做法**：后台操作一律改为**命令事件**——View 回调只 `mvl_evt_publish(EVT_CMD_*, ...)`，由目标任务以 `MVL_EVT_CTX_TASK` 订阅后在自己的上下文执行（[design.md](../design/design.md) §5.5）。需要结果回显时再发布结果事件。同理，`mvl_msg` 回调内禁止 `vTaskDelay()` 与任何带超时的阻塞等待。

### P6 ISR 中误用任务级接口 —— 中断里死机 【致命】

- **现象**：某中断触发后系统死机 / 断言失败。
- **根因**：ISR 中调用了 `mvl_msg_post()` / `mvl_evt_publish()`（任务级），其内部可能阻塞，而 ISR 禁止阻塞。
- **正确做法**：ISR 路径只用 `_isr` 后缀版本（`mvl_msg_post_isr()` / `mvl_evt_publish_isr()`）。注意 ISR 版发布事件时订阅者越多耗时越长，重订阅者的 ISR 发布要控制频率。

## 二、高级

### P7 事件载荷超 8 字节或含指针 —— 数据错乱 【高】

- **现象**：订阅者收到的数据被截断 / 是垃圾值；或间歇性崩溃。
- **根因**：`mvl_evt_data_t` 是固定 8 字节的 union，发布时值拷贝。两种违规：① 试图塞超过 8 字节的数据（数组、长字符串），放不进去或被截断；② 在 `raw[8]` 里藏一个指向易失内存的指针——值拷贝拷的是**指针本身**，指向的内存在订阅者执行时可能已失效，P3 的生命周期问题换了个马甲回来。
- **正确做法**：载荷只放 ≤ 8 字节的值（`i32` / `u32` / `f32` / `bool` / 短位图）。大数据走「**就绪事件 + Model 快照**」：数据本体写 Model，事件只作通知，订阅者经 `snapshot()` 读本体（[design.md](../design/design.md) §5.4）；纯 `mvl_msg` 场合用双缓冲 + 指针。

### P8 订阅晚于事件到达 / 初始化顺序覆盖订阅表 —— 事件全丢 【高】

- **现象**：UI 完全不刷新，事件像石沉大海；`mvl_evt_publish()` 返回 `true` 但没有任何订阅者收到。
- **根因**（两种都见过真机事故）：
  - ① 后台任务先跑起来发布事件，订阅表还没注册，事件无人接收，静默丢失；
  - ② `mvl_evt_init()` 会**清零整张订阅表**。真机踩坑：总线初始化挂在 UI 加载流程里，而网络管理模块在 `app_main` 早期就完成订阅——订阅表随后被总线初始化的清零覆盖，事件全部丢失。
- **正确做法**：严格按启动顺序（[design.md](../design/design.md) §7）：`mvl_msg_init()` → `mvl_evt_init()` → Model 初始化 → ViewModel 完成全部订阅 → **最后**创建会发布事件的后台任务。基础设施 init（前三步）在 `app_main` 集中完成，且先于任何会订阅 / 发布事件的模块初始化。

### P9 ISR 投递队列满静默丢消息 —— 关键告警丢失 【高】

- **现象**：高频中断场景下，偶发 UI 不更新 / 告警不显示，无日志无断言。
- **根因**：`mvl_msg_post_isr()` 在队列满时消息被**静默丢弃**（ISR 不能阻塞，只能丢）。
- **正确做法**：队列深度按峰值估算（生产者数 × 单周期最多投递条数）；高频 ISR 源先合并降频（[design.md](../design/design.md) §8）；真正关键的告警改由任务级阻塞投递（ISR 只通知任务）。事件总线路径的丢弃会计入 `mvl_evt_drop_count()`，调试期接入日志，正常系统应恒为 0。

### P15 Model setter 先发布事件后写状态 —— 订阅者读到旧快照 【高】

- **现象**：订阅者收到事件后读快照，拿到的却是**旧值**；UI 间歇性显示过期数据，与任务调度时序相关，难复现。
- **根因**：「先写状态、后发事件」是快照模式的正确性契约。顺序颠倒时窗口真实存在：对 `MVL_EVT_CTX_TASK` 订阅者，`mvl_evt_publish()` 内部的队列发送会立即唤醒订阅任务（SMP 平台上它甚至正在另一核并行运行），此刻状态还没写入，`snapshot()` 必然是旧值；LVGL 订阅者虽经异步分发，发布核在 publish 与写状态之间被抢占同样会撕开窗口。
- **正确做法**：setter 固定三段式——互斥锁内写完全部相关字段 → 解锁 → `mvl_evt_publish()`，保证「事件到达订阅者时快照必为新值」。模板与 mvl-gen 生成的 setter 已遵循此序，手写 setter 不得颠倒，也不得把部分字段的写拆到 publish 之后。

## 三、中级

### P10 托管组件主循环不可改 / 移植层锁超时语义误读 【中】

- **现象 A**：LVGL 主循环由 esp_lvgl_port 等托管组件拥有（`lvgl_port_task` 内部 `lock → lv_timer_handler() → unlock`），无处插入 `mvl_msg_process()`；直接改组件源码则升级时被覆盖。
- **现象 B**：用 `lvgl_port_lock(0)` 想「试一下就走」，结果任务被永久挂起。
- **根因**：A 是接入形态问题；B 是超时语义误读——esp_lvgl_port 的 `lvgl_port_lock(0)` 中 `0` 表示**无限等待**（映射为 `portMAX_DELAY`），并非「不等待」。
- **正确做法**：A：在 LVGL 任务上下文创建 `lv_timer` 周期调用 `mvl_msg_process()`（运行在 `lv_timer_handler()` 定时器阶段、渲染之前，语义等价，零侵入组件），见 [design.md](../design/design.md) §6.2。启动期从其他任务（如 `app_main`）创建该分发定时器时，`lv_timer_create` 本身也是 LVGL API，调用须用移植层锁包裹（如 `lvgl_port_lock(1000)`）。B：需要可超时语义时传**正数毫秒**并检查返回值；启动期在其他任务中创建控件（LVGL 任务已在运行）时，用移植层锁包裹建树过程（如 `lvgl_port_lock(1000)`）。

### P11 `mvl_msg_process()` 放在渲染之后 —— UI 慢一帧 【中】

- **现象**：UI 更新总比预期慢一拍，数据源明明已经变了。
- **根因**：主循环里 `mvl_msg_process()` 放在了 `lv_timer_handler()` **之后**，本周期的修改要等下个周期才被渲染。
- **正确做法**：调换顺序——先 `mvl_msg_process()` 消费全部消息，再 `lv_timer_handler()` 统一渲染当帧（[design.md](../design/design.md) §6.1）。

### P12 高频源逐点投递 —— 队列刷屏挤占渲染 【中】

- **现象**：1 kHz 传感器每毫秒投递一次，UI 反而卡顿、丢帧，甚至触发 P9 式丢弃。
- **根因**：UI 只需要 10 Hz 刷新，99% 的投递是无效功；消息队列 / 投递池被刷屏，挤占 LVGL 主任务的渲染时间。
- **正确做法**：「最新值 + 低频消费」——生产者只写 `volatile` 最新值，由 `lv_timer` 或低频投递按 UI 帧率刷新（[design.md](../design/design.md) §8）；或用 `mvl_msg_try_post()` 允许丢弃。事件频率不应超过 UI 帧率。

### P16 状态 / 事件设计了但生产者从未驱动 —— 僵尸状态与 UI 死分支 【中】

- **现象**：某个状态对应的 UI 分支（如「进行中」提示）永远不出现；静态检查全部通过，其余功能正常，问题长期潜伏。
- **根因**：代码生成器的静态检查只保证**接线合法**（ID 不撞号、载荷合规、无 LVGL → LVGL 自环等），不保证状态机被完整驱动。字段有 setter 在用、事件有订阅者，孤儿检查不会报警；但某个枚举值 / 某个事件可能没有任何生产者真正触达，只能人工发现。
- **正确做法**：状态机走查——每个状态枚举值至少有一个 `set_xxx()` 调用点（全局搜索验证）；评审生成的接线报告（`wiring_report.md`）时，核对每个事件的生产者真实存在且会在运行期触发；提测前逐项触发每个 UI 显示分支。

### P17 yaml 的 `config` 段与 C 侧配置宏是两份事实 —— 调容量不生效 【中】

- **现象**：在接线 yaml 里把 `lvgl_job_pool` 调大，重新生成、烧录，丢事件依旧；`mvl-gen check` 全部通过，但运行行为没有任何变化。
- **根因**：yaml 的 `config` 段**只进入静态检查**（如 C3 判断 ISR → LVGL 路径是否配置了投递池），生成器不会把它写进任何 C 代码。运行期实际容量由 `mvl_config.h` 的默认值或构建期 `-D` 覆盖决定（[porting.md](porting.md) 配置宏表）——两处是手工保持一致的两份事实。
- **正确做法**：调整容量时两侧同步：yaml `config`（供检查器）+ 构建系统 `-DMVL_EVT_LVGL_JOB_POOL_SIZE=N`（供运行），并在 yaml 注释中标注对应关系；改完后 `mvl-gen check` 与 `mvl_evt_drop_count()` 实测双重验证。

### P18 契约容量与生产者缓冲是两份常量 —— 只改一处 【中】

- **现象**：调大 Model 契约里的列表容量后，结果仍按旧容量被截断；或反向——生产者上报的条数超过契约容量，靠 setter 内的防御性钳制才没有越界。
- **根因**：契约类型中的容量宏（经 yaml `types` 段进入 Model 头文件）与生产者 / 驱动模块内部的缓冲宏是**两份手工同步的定义**，没有单一事实源，改一处忘改另一处。
- **正确做法**：容量宏只定义在契约头（yaml `types` 段），生产者 include 契约头引用同一宏；架构上实在无法共用时，用 `_Static_assert` 在构造期校验两边相等（生成物 `mvl_events.h` 对 `MVL_EVT_MAX_ID` 已有同样做法），把「忘记同步」变成编译错误。

### P19 任务订阅队列浅 + 发布不等待 —— 命令事件静默丢失 【中】

- **现象**：用户快速重复操作（连点按钮）时偶发「点了没反应」，无日志、无断言；慢速操作完全正常。
- **根因**：`MVL_EVT_CTX_TASK` 订阅者经自身队列接收事件，发布侧的队列发送**不等待**（满即丢，计入 `mvl_evt_drop_count()`）；生成的任务骨架队列深度是固定值，高频命令场景下深度不足，命令被静默丢弃。
- **正确做法**：命令类事件在 UI 侧防抖 / 合并（前一条命令未消费完时忽略或合并重复触发）；按峰值速率评估订阅队列深度与 `MVL_EVT_LVGL_JOB_POOL_SIZE`；调试期 `mvl_evt_drop_count()` 应恒为 0；真正关键的命令配应用层确认 / 重发机制。

## 四、GUI Guider 生成工程专项

以下两条来自真机崩溃记录，仅适用于 GUI Guider 生成工程（`setup_ui()` / `ui_load_scr_animation()` 形态）。

### P13 跨页读写懒创建界面的控件 —— LoadProhibited 【致命】

- **现象**：在界面 A 的回调里写界面 B 的控件（`lv_label_set_text(guider_ui.screen_B_label_xxx, ...)`），若 B 从未被加载过，`LoadProhibited` 崩溃。
- **根因**：GUI Guider 工程界面是**懒创建**的——`setup_ui()` 只创建主屏，其余界面在首次切换时才由 `ui_load_scr_animation()` 内的 `if (new_scr_del) setup_scr(ui)` **同步**创建。未加载过的界面，其控件指针全为 NULL。
- **正确做法**：**先 `ui_load_scr_animation()` 切屏**（同步返回后 B 的控件已存在），**再读写 B 的控件**；跨页访问加 NULL 防御。

### P14 动态列表项不继承设计期字体 —— 文本变占位框 【中】

- **现象**：`lv_list` 运行时经 `lv_list_add_btn()` 新建的项，中文等自定义字体文本显示为占位框（豆腐块）。
- **根因**：Guider 对 list 的 `extra_btns` / `extra_texts` 样式只挂在设计期生成的静态 item 上；运行时清空列表后新建的按钮 / 标签回退到主题默认字体，自定义字库（如分区加载的中文字库）缺字形。
- **正确做法**：动态创建的列表项显式 `lv_obj_set_style_text_font()`（创建后遍历其子控件设置）。
